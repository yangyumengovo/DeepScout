# DeepScout 设计决策记录（ADR）

记录项目中的关键取舍与踩坑。格式：问题 -> 备选方案 -> 决策 -> 理由。面试时这部分比代码本身更能体现工程判断力。

---

## 1. 编排：为什么用 LangGraph 而不是裸 while 循环

**问题**：调研流水线有 7 个阶段，可以用一个循环 + if/else 串起来。

**决策**：LangGraph StateGraph，节点间显式传递 `ResearchState`。

**理由**：
- 每个节点（plan / retrieve / index / outline / write / verify / assemble）职责单一，可以单独单测（如 `tests/test_graph_mock.py` 按节点名断言事件序列）；
- 状态是显式的 TypedDict，而不是散落在循环里的局部变量，出问题可以从 trace 还原任意一步；
- 节点粒度天然对应 trace 归因粒度——「报告不好」可以先定位到是 retrieve 慢/空，还是 write 幻觉；
- 未来接 checkpointer 做断点续跑、或把 write 并行化，图结构改起来最小。

代价：引入框架依赖与学习成本；对两三个节点的极简场景确实过重。本项目节点数和状态复杂度足以摊薄这个成本。

## 2. 踩坑：为什么自实现 BM25 而不用 rank_bm25

**现象**：单元测试中两文档的小语料上，查询词明明命中，`rank_bm25.BM25Okapi.get_scores` 却返回全 0，检索结果为空。

**定位**：`rank_bm25` 的 IDF 公式是 `log((N - df + 0.5) / (df + 0.5))`。当词项出现在恰好一半文档（df = N/2）时，该式等于 `log(1) = 0`——小语料上大量常见词的 IDF 被精确清零，得分全空。一次调研的证据库通常只有几十个块，正好落在这个陷阱的高发区。

**决策**：自实现 Lucene 风格 BM25（~40 行），IDF 用 `log(1 + (N - df + 0.5) / (df + 0.5))`，恒为正，大小语料行为一致；并把该场景固化为回归测试（`test_index_search_ranks_relevant_chunk_first`）。

**教训**：LLM 应用的检索层坑常在「库的默认行为 × 你的数据规模」的交叉处，端到端跑通不代表检索在工作——必须给检索层写独立断言。

## 2.5 踩坑：幽灵依赖（numpy）——为什么 CI 第一次是红的

**现象**：本地 24 个测试全绿，推上 GitHub 后 CI 失败：`ModuleNotFoundError: No module named 'numpy'`（evidence.py 检索路径里 `import numpy`）。

**定位**：numpy 不在 pyproject 依赖声明里，本地能跑只是因为虚拟环境中某个包恰好传递安装了它——典型的幽灵依赖；CI 的干净环境立刻暴露。

**决策**：BM25 路径改纯 Python 实现（证据库是单次调研的几十个块，纯 Python 足够且更轻）；numpy 仅保留在向量混合检索分支（该分支由 `fastembed` 可选依赖启用，其自身依赖 numpy），基础安装零 numpy。

**教训**：声明依赖必须与代码真实 import 一致；「本地能跑」不是依赖完整的证据，干净环境的 CI 才是。

## 3. 为什么引用核验（verify）是独立节点

**问题**：让写报告的模型「自己注意引用准确」是否就够了？

**决策**：拆出独立 verify 节点，把每条 `[E_n]` 引用与其证据原文配对，由一次独立 LLM 调用判定 supported / partial / unsupported，结果进报告附录。

**理由**：
- 生成与评判分离，是评测领域的基本原则（不能让被测对象自己给自己打分）；
- 核验结果量化（通过率）后，prompt 版本、检索策略的改动有了可比较的指标；
- 核验温度设为 0、prompt 明确「宁可判 partial」，降低核验者自己放水。

**已知局限**：核验者仍是 LLM，可能误判；通过率是参考信号而非保证（README 局限一节如实声明）。

## 4. 为什么 mock 模式是一等公民

**决策**：FakeLLM 按提示词中的角色标记回放确定性剧本 + MockSearchProvider 基于内置演示语料 + demo:// 协议抓取本地文件，三者让整条流水线（含真实 Function Calling 路径）在无网络、无 key 环境下端到端运行。

**理由**：
- CI 无密钥全绿，「测试不依赖外部服务」和普通后端是同一工程标准；
- 剧本即文档：读 `fake.py` 就能看懂每个节点期望的输入输出形态；
- 开发期不烧钱不撞限流；演示可复现（CI 与本地行为一致）。

**代价**：剧本与 prompt 中的角色标记耦合（标记改动需同步剧本），在 `prompts.py` 中显式注释了这层契约。

## 5. 工具层为什么自己写注册器而不用框架内置

**决策**：pydantic 模型声明参数 -> 自动生成 OpenAI tools JSON Schema -> 统一 `call()` 入口（校验 + 错误转 JSON 回给模型）。

**理由**：
- 参数校验与给模型的 Schema 出自同一份声明，永不脱节；
- 工具执行「永不抛异常」：错误以 JSON 返回给模型，让 Agent 自己决定重试还是放弃——这是工具调用鲁棒性的关键细节；
- 代码量 ~100 行，完全可控可讲清，避免「会用框架但说不清原理」。

## 6. LLM 客户端为什么做三层（真实 / 缓存 / Fake）

- **OpenAICompatClient**：换供应商只改环境变量（DeepSeek/GLM/Qwen/本地 vLLM），业务代码零改动——供应商锁定是 LLM 应用的常见隐性债务；
- **DiskCacheClient**：装饰器模式，按请求哈希缓存响应，开发期重复调试不重复计费，评测期关掉保证新鲜；
- **FakeLLM**：见第 4 条。

三层实现同一 `LLMClient` 协议，依赖注入进图，测试想换哪层换哪层。

## 7. 上下文与成本控制（当前做法与不足）

当前：网页正文截断 6000 字符入上下文、工具结果摘要 4000 字符、分块 500 字符、单子问题抓取上限、总工具步数上限、trace 记录 token 与估算成本。

不足（如实记录）：多轮压缩、分层摘要、按证据相关度的动态预算尚未做，超大规模调研会退化——见 Roadmap。

## 8. 首次真实评估：发现与两轮 Prompt 迭代（2026-10-16，GLM-4-Flash）

评估不是为了出一张好看的表，而是为了暴露问题。首次真实运行（q01，19 次 LLM 调用 / 26873 token / 195s）暴露了三个问题，各对应一轮修复：

**发现 1：来源集中。** 7 条引用中 6 条来自同一篇 CSDN 博客（不同分块）。
**修复（v1.1）**：检索员 prompt 传入已抓取链接清单，明确「优先选择不同站点」；评测新增 `unique_sources` 指标监控。

**发现 2：格式噪声。** 撰写节点会把章节标题再抄一遍；核验理由输出长段英文。
**修复（v1.1）**：撰写者加「禁止重复标题」；核验员限定「中文、≤40 字」。

**发现 3（最重要）：边界题不拒答。** 两道虚构对象题（不存在的产品、不存在的 2027 论文）均未如实声明信息不足，模型把「主题相邻」的真实论文编织成虚构对象的内容——核验通过率跌至 14%（verify 节点把这个幻觉暴露了出来，这本身验证了它的价值）。
**修复（v1.2）**：检索员与撰写者增加「证据必须明确提到题目中的具体对象，仅同主题泛泛页面不算支撑」的约束；拒答判定词库补充「资料不足」等变体。

**迭代效果（边界题 2 道）：**

| 指标 | v1 | v1.2 |
|---|---|---|
| 拒答命中率 | 0% | **100%** |
| b02（虚构论文）核验通过率 | 14% | **56%** |

**v1.3：对象锚点硬校验（机制级修复）。** prompt 约束只能缓解幻觉，改为代码机制：`question_anchors()` 从题目提取对象锚点（引号内完整名称 + 形态独特的拉丁串：混合大小写/连字符/末位数字/全大写缩写），撰写节点仅允许引用**文本中实际包含锚点**的证据块（`filter_by_anchors`）；宽泛的纯中文问题无锚点、不受影响。配套 6 个单元测试。

**边界题三轮对比：**

| 指标 | v1 | v1.2（软约束） | v1.3（硬校验） |
|---|---|---|---|
| 拒答命中率 | 0% | 100% | **100%** |
| b02（虚构论文）核验通过率 | 14% | 56% | **62.5%** |
| b01（虚构产品）核验通过率 | 50% | 40% | 0%* |

\* b01 的 0% 是核验员对「锚点碰撞」的如实暴露：某真实工具清单页恰好包含 "ResearchBot" 字样，通过了硬校验进入引用，但其内容与题目对象无关——verify 作为最后一道防线全部判为 partial/unsupported，报告同时保留了「评测信息尚不充分」的声明。**已知局限**：单词锚点（Ultra / ResearchBot）存在碰撞可能，后续可要求多锚点共现或锚点别名校验。gate 减少暴露面、verify 暴露残余——分层防御，与安全工程同构。

**综合题消融复测**（3 道，验证「规划模块价值在复杂任务」的假设）：

| 配置 | 关键词覆盖 | 唯一来源数 | token |
|---|---|---|---|
| full | **1.0** | **4.0** | 37342 |
| no-plan | 0.778 | 2.0 | 20328 |
| no-verify | 1.0 | 2.0 | 33391 |
| naive | 0.889 | 2.0 | 18751 |

假设证实：宽泛综合题上规划模块覆盖率 +22pp、来源多样性翻倍；而简单事实题上（前次消融）规划是负收益。**结论：任务复杂度决定配置取舍，没有全局最优配置——这正是消融实验相对「感觉有用」的价值。**

**遗留（如实记录）**：小参数模型（glm-4-flash）在锚点碰撞场景下仍会被动引入无关内容；核验通过率在综合题上整体偏低（更多论断更难全支撑），反映覆盖率与支撑率的权衡。评估报告见 `eval/report_*.md`。

## 9. Rerank 接入：RAG 三层的第二层（召回 -> 重排 -> 引用）

**问题**：BM25（+可选向量）召回按词面/嵌入相似度排序，前 8 块里常混有「词面命中但语义跑偏」的块，撰写节点会引用它们拉低核验通过率。

**决策**：可插拔 cross-encoder 重排（fastembed + bge-reranker-v2-m3，多语言、本地 ONNX 推理免费）。开启时召回池扩到 10，重排后取 top-6 进 prompt；**未开启时代码路径与 v1.3 逐字节一致（k=8、不截断）**——消融对比只差 rerank 一个变量。

**工程要点**：
- 优雅降级：未配置/依赖缺失/模型下载失败/类名随版本变更，一律返回 None 跳过重排，主流程不受可选组件影响（单测固化）；
- 模型级缓存：同进程多次运行不重复加载；
- fastembed 新旧版本 cross-encoder 类名不同（TextCrossEncoder / TextCrossEncode），按新路径导入、失败即降级。

**消融结果**：见 README「评测」节 full vs full+rerank 对照（事实题 3 道）。
